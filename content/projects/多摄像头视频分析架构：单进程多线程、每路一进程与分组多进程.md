# 多摄像头视频分析架构：单进程多线程、每路一进程与分组多进程

在视频分析系统中，每接入一台摄像头，通常都需要完成一条处理链路：

```
视频接入 → 解码与抽帧 → 模型推理 → 跟踪与业务规则 → 事件输出
```

当摄像头从一路增加到多路，系统很快会遇到一个架构问题：应该为每台摄像头创建一个线程，还是一个进程？

这个问题没有统一答案。线程和进程决定了资源如何共享、故障会影响多大范围，以及系统如何扩容。理解这些差异，比记住某种“标准做法”更有用。

本文以通用的实时视频分析业务为例，介绍三种方案：

- 单进程、多摄像头线程。
- 每路摄像头一个进程。
- 每个进程管理一组摄像头。

文中的 Python 代码用于说明关键结构，视频解码、模型接口和事件存储通过抽象接口表示，接入具体库后即可进一步实现。

## 一、先建立统一的业务模型

假设系统需要接入多路网络摄像头，持续分析最新画面，并输出识别事件。

每路摄像头包含两类工作。

**采集工作**负责连接设备、读取视频、解码和重连。这部分既涉及网络等待，也涉及解码计算。

**分析工作**负责预处理、模型推理，以及有状态的跟踪和业务判断。

这两类工作的速度通常不同。例如，摄像头每秒提供 25 帧，业务只需要分析其中 5 帧。如果直接把所有帧放进无界队列，处理速度稍慢就会积压，最终分析的是几秒甚至几十秒以前的画面。

对于强调时效性的业务，可以让每路摄像头只保留最新待处理帧：

```
采集端持续读取
      ↓
最新帧槽：旧帧被新帧覆盖
      ↓
分析端处理完成后取下一帧
```

这种策略主动放弃部分帧，以限制应用层积压。它不适用于必须逐帧处理的录像分析，也不能自动消除摄像头、网络和解码器内部的缓冲。

### 一个可复用的最新帧槽

```python
import threading
import time
from dataclasses import dataclass


@dataclass
class Frame:
    camera_id: str
    image: object
    received_at: float


class LatestFrameSlot:
    def __init__(self):
        self._condition = threading.Condition()
        self._frame = None
        self._closed = False

    def put(self, frame):
        with self._condition:
            if self._closed:
                return

            self._frame = frame
            self._condition.notify()

    def take(self, timeout=0.5):
        with self._condition:
            self._condition.wait_for(
                lambda: self._frame is not None or self._closed,
                timeout=timeout,
            )

            frame = self._frame
            self._frame = None
            return frame

    def close(self):
        with self._condition:
            self._closed = True
            self._condition.notify_all()
```

`take()` 会取走当前帧。分析期间，新到达的帧可以覆盖槽中的旧帧，而不会形成越来越长的队列。

三种架构都可以使用这一机制。它们真正的区别，是这些采集和分析单元被放在哪些进程中。

## 二、模式一：单进程、多摄像头线程

这种模式将所有摄像头放在同一个进程里，每路维护自己的处理线程和业务状态。

一种直观实现是每路两个线程：

```
视频分析进程
├── 摄像头 A
│   ├── 采集线程 → 最新帧槽
│   └── 分析线程 → 模型 → 跟踪 → 规则
├── 摄像头 B
│   ├── 采集线程 → 最新帧槽
│   └── 分析线程 → 模型 → 跟踪 → 规则
└── 摄像头 C
    ├── 采集线程 → 最新帧槽
    └── 分析线程 → 模型 → 跟踪 → 规则
```

“一路两个线程”是本文采用的实现方案，并不是该模式的硬性要求。也可以使用每路一个线程，或者多个采集线程搭配有限数量的分析线程。

### 具体实现

首先定义单路处理单元：

```python
class CameraPipeline:
    def __init__(
        self,
        camera,
        source_factory,
        analyzer_factory,
        event_sink,
        stop_event,
    ):
        self.camera = camera
        self.source_factory = source_factory
        self.analyzer_factory = analyzer_factory
        self.event_sink = event_sink
        self.stop_event = stop_event

        self.slot = LatestFrameSlot()
        self.threads = []

    def start(self):
        self.threads = [
            threading.Thread(
                target=self._capture_loop,
                name=f"capture-{self.camera['id']}",
            ),
            threading.Thread(
                target=self._analyze_loop,
                name=f"analyze-{self.camera['id']}",
            ),
        ]

        for thread in self.threads:
            thread.start()

    def _capture_loop(self):
        # source_factory 应提供连接、读帧超时和重连能力。
        source = self.source_factory(self.camera)

        try:
            while not self.stop_event.is_set():
                image = source.read(timeout=1.0)
                if image is None:
                    continue

                self.slot.put(
                    Frame(
                        camera_id=self.camera["id"],
                        image=image,
                        received_at=time.monotonic(),
                    )
                )
        finally:
            source.close()

    def _analyze_loop(self):
        # 每路独立持有跟踪和规则状态。
        analyzer = self.analyzer_factory(self.camera)

        try:
            while not self.stop_event.is_set():
                frame = self.slot.take(timeout=0.5)
                if frame is None:
                    continue

                events = analyzer.process(frame)

                for event in events:
                    self.event_sink.emit(event)
        finally:
            analyzer.close()

    def close(self):
        self.slot.close()

    def join(self, timeout=3.0):
        for thread in self.threads:
            thread.join(timeout=timeout)
```

然后在一个进程中启动多路：

```python
def run_group(
    cameras,
    stop_event,
    source_factory,
    analyzer_factory,
    sink_factory,
):
    # 每个进程在内部创建自己的连接资源。
    sink = sink_factory()

    pipelines = [
        CameraPipeline(
            camera,
            source_factory,
            analyzer_factory,
            sink,
            stop_event,
        )
        for camera in cameras
    ]

    try:
        for pipeline in pipelines:
            pipeline.start()

        while not stop_event.wait(1.0):
            # 示例采取 fail-fast：
            # 任一处理线程异常退出，让整个组退出，由上层重建。
            if any(
                not thread.is_alive()
                for pipeline in pipelines
                for thread in pipeline.threads
            ):
                raise RuntimeError("camera thread exited")
    finally:
        stop_event.set()

        for pipeline in pipelines:
            pipeline.close()

        for pipeline in pipelines:
            pipeline.join()

        sink.close()
```

这里的 `event_sink` 会被多个分析线程调用，因此必须支持线程安全访问，或者内部通过有界队列交给专门的事件输出线程处理。

### 优点：共享资源直接，实现成本低

线程共享进程内存，不需要为了传递画面而引入进程间通信。

同一帧图像可以通过内存引用交给分析线程；配置、连接池和缓存也比较容易复用。

但“在同一个进程里”不等于“自动共享模型”。如果每路分别创建模型实例，仍然会产生多份模型资源。若希望共享同一个模型，需要确认推理后端的并发调用约束，并处理可变输入缓冲等问题。

### 局限：故障边界是整个进程

单路发生普通异常时，可以通过异常处理或线程重建恢复。

但如果视频解码或推理的原生库发生进程级崩溃，同进程的其他摄像头也会停止。某个线程如果卡在底层调用中，Python 也没有通用、安全的方式强行终止它。

因此，这种模式需要认真配置读帧超时，并监控每路实际处理进度。仅检查进程是否存活是不够的。

### Python 多线程能否利用多核？

在启用 GIL 的常规 CPython 中，纯 Python 的计算密集代码难以通过线程获得多核并行收益。

不过视频分析通常还包含网络 I/O、原生解码和推理库。这些部分是否释放 GIL、如何创建内部线程，取决于具体实现，不能简单地认为“Python 线程只能使用一个核心”。

例如，ONNX Runtime 的 Session 自身就可能使用多个计算线程。因此，应用层创建十个分析线程，实际操作系统线程数可能远高于十个。[ONNX Runtime 线程管理文档](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

## 三、模式二：每路摄像头一个进程

这种模式将每路摄像头放进独立进程：

```
管理进程
├── 摄像头 A 进程
│   ├── 采集线程
│   └── 分析线程
├── 摄像头 B 进程
│   ├── 采集线程
│   └── 分析线程
└── 摄像头 C 进程
    ├── 采集线程
    └── 分析线程
```

注意，每路一个进程与进程内使用线程并不冲突。进程负责隔离，线程负责组织一路内部的采集与分析。

### 具体实现

前面的 `run_group()` 可以直接复用：每个子进程只传入一台摄像头。

```python
import multiprocessing as mp


def camera_process_entry(camera, stop_event):
    run_group(
        cameras=[camera],
        stop_event=stop_event,
        source_factory=create_source,
        analyzer_factory=create_analyzer,
        sink_factory=create_event_sink,
    )


def start_camera(ctx, camera):
    stop_event = ctx.Event()

    process = ctx.Process(
        target=camera_process_entry,
        args=(camera, stop_event),
        name=f"camera-{camera['id']}",
    )
    process.start()

    return process, stop_event
```

管理进程保存摄像头与子进程的对应关系，发现退出后重新创建：

```python
def supervise(cameras, shutdown_event):
    ctx = mp.get_context("spawn")

    children = {
        camera["id"]: {
            "camera": camera,
            "process": None,
            "stop": None,
            "retry_at": 0.0,
            "backoff": 1.0,
        }
        for camera in cameras
    }

    try:
        while not shutdown_event.wait(0.5):
            now = time.monotonic()

            for item in children.values():
                process = item["process"]

                if process is not None and process.is_alive():
                    continue

                if process is not None:
                    process.join()
                    process.close()
                    item["process"] = None
                    item["retry_at"] = now + item["backoff"]
                    item["backoff"] = min(item["backoff"] * 2, 30.0)

                if now < item["retry_at"]:
                    continue

                process, stop_event = start_camera(
                    ctx, item["camera"]
                )
                item["process"] = process
                item["stop"] = stop_event

    finally:
        for item in children.values():
            if item["stop"] is not None:
                item["stop"].set()

        for item in children.values():
            process = item["process"]
            if process is None:
                continue

            process.join(timeout=5)

            if process.is_alive():
                process.terminate()
                process.join(timeout=2)

            if process.is_alive():
                process.kill()
                process.join()

            process.close()
```

以上代码展示退出检测、退避重启和分级停止。完整系统还应增加持续稳定运行后重置退避、重启频率告警，以及处理超时检测。

`spawn` 需要进程入口函数可导入，启动逻辑必须放在主入口保护中：

```python
if __name__ == "__main__":
    shutdown_event = threading.Event()

    try:
        supervise(load_cameras(), shutdown_event)
    except KeyboardInterrupt:
        shutdown_event.set()
```

模型、视频连接和消息客户端都应在子进程内部初始化，避免跨进程复用已经打开的运行时资源。Python 官方文档说明了不同启动方式及对象传递的约束。[Python multiprocessing 文档](https://docs.python.org/3/library/multiprocessing.html)

### 优点：单路可以独立恢复

摄像头 A 的解码库崩溃时，摄像头 B 和 C 的进程仍可以继续运行。

某路卡死时，管理进程也可以终止该路进程并重建。这比尝试停止一个阻塞线程更可控。

但进程隔离不是完整的资源隔离：多个进程依然会争抢同一台机器的 CPU、内存、网络和 GPU。需要限制资源时，还要结合操作系统或容器提供的机制。

### 代价：模型和运行时资源容易重复

如果每路都创建模型实例，摄像头数量越多，模型、工作缓冲和运行时资源也越多。

粗略估算可以写成：

```
总内存 ≈ 摄像头数量 ×
        （进程基础开销 + 模型资源 + 单路缓冲和状态）
```

这个公式只是预算模型，实际物理内存还会受到共享库、内存映射和后端分配策略影响，应通过测量确认。

对于 GPU，多进程还可能引入多份模型显存与运行上下文。进程越多并不代表推理吞吐一定越高。

### 尽量让原始画面留在子进程内

每路已经独立完成分析时，通常只需要向外发送识别事件和状态，无须把每帧图像传回管理进程。

例如，一张 1920×1080、三通道、每通道一个字节的图像，未压缩大小约为：

```
1920 × 1080 × 3 ≈ 6.22 MB
```

若每秒传递 5 张，仅单路原始像素数据就约为 31 MB/s，还没有计算序列化和复制成本。

Python 的 `multiprocessing.Queue` 会序列化放入其中的对象，因此大量传递原始图像需要谨慎评估。官方还提醒，在进程使用队列时强行终止它，可能损坏队列。[Python 多进程队列说明](https://docs.python.org/3/library/multiprocessing.html)

## 四、模式三：每个进程管理一组摄像头

分组模式将多路摄像头分配到若干进程中，每个进程内部继续使用线程：

```
管理进程
├── 分析进程 1
│   ├── 摄像头 A：采集线程 + 分析线程
│   └── 摄像头 B：采集线程 + 分析线程
├── 分析进程 2
│   ├── 摄像头 C：采集线程 + 分析线程
│   └── 摄像头 D：采集线程 + 分析线程
└── 分析进程 3
    ├── 摄像头 E：采集线程 + 分析线程
    └── 摄像头 F：采集线程 + 分析线程
```

它让故障影响范围落在一个组内，同时减少进程数量。

### 具体实现

组内仍然复用 `run_group()`：

```python
def group_process_entry(cameras, stop_event):
    run_group(
        cameras=cameras,
        stop_event=stop_event,
        source_factory=create_source,
        analyzer_factory=create_analyzer,
        sink_factory=create_event_sink,
    )
```

创建子进程时，传入一组摄像头：

```python
def start_group(ctx, group_id, cameras):
    stop_event = ctx.Event()

    process = ctx.Process(
        target=group_process_entry,
        args=(cameras, stop_event),
        name=f"group-{group_id}",
    )
    process.start()

    return process, stop_event
```

管理逻辑与每路一进程基本相同，只是管理对象从 `camera_id` 变成 `group_id`。进程退出时，重新启动整个组。

最简单的分组方法是按固定数量切分：

```python
def split_groups(cameras, group_size):
    return [
        cameras[index:index + group_size]
        for index in range(0, len(cameras), group_size)
    ]
```

固定数量分组容易实现，但实际负载未必均匀。同样是一路摄像头，分辨率、编码格式、分析频率和模型复杂度都可能不同。

更合理的方法是根据压测得到的负载权重分配：

```python
def balance_groups(cameras, group_count):
    groups = [[] for _ in range(group_count)]
    loads = [0.0] * group_count

    for camera in sorted(
        cameras,
        key=lambda item: item["estimated_load"],
        reverse=True,
    ):
        index = min(
            range(group_count),
            key=lambda i: loads[i],
        )

        groups[index].append(camera)
        loads[index] += camera["estimated_load"]

    return groups
```

这是一个简单的静态均衡策略。权重应该来自实际测量，例如单路目标分析频率下的 CPU 占用或推理时间，而不是只看分辨率。

### 分组不会自动减少模型份数

这是该模式最容易被误解的地方。

假设 12 路摄像头分成 3 个进程，每个进程管理 4 路。如果每路仍然创建自己的模型实例，模型依旧可能有 12 份。

要减少模型资源，需要进一步改变组内推理方式：

```
一个分析进程
├── 多路采集线程
├── 每路最新帧槽
└── 一个共享推理执行器
    ├── 公平选择各路待处理帧
    ├── 执行模型推理
    └── 按 camera_id 分发结果
```

此时可以让每个进程只加载一份模型，但也引入新的调度问题：

- 一路视频不能长期占据推理执行器。
- 推理结果必须对应正确的摄像头和帧。
- 每路跟踪与规则状态仍需独立维护。
- 采用批处理时，需要限制等待时间，避免为了凑 batch 增加延迟。

所以，**进程分组与模型共享是两个独立决策**。

## 五、三种模式的核心对比

| 对比项                 | 单进程、多线程       | 每路一个进程       | 每进程管理一组           |
| ---------------------- | -------------------- | ------------------ | ------------------------ |
| 进程数量               | 1 个业务进程         | 大致等于摄像头数量 | 大致等于分组数量         |
| 进程级崩溃影响         | 所有摄像头           | 单路               | 组内摄像头               |
| 强制恢复阻塞任务       | 通常需要重启整个进程 | 可重启单路进程     | 可重启整组进程           |
| 内存共享               | 最直接               | 需要进程间通信     | 组内直接共享             |
| 基础运行时开销         | 较低                 | 较高               | 居中                     |
| 模型资源份数           | 取决于实例组织       | 通常每路独立       | 取决于组内推理设计       |
| 纯 Python CPU 计算并行 | 受 GIL 配置影响      | 可利用多个进程     | 可利用多个进程           |
| 管理复杂度             | 较低                 | 需要维护大量进程   | 需要维护进程和分组       |
| 独立调整单路配置       | 容易                 | 容易               | 容易，但迁移需处理组归属 |
| 适用重点               | 简单、共享方便       | 单路隔离与恢复     | 资源和故障范围之间的平衡 |

这里的“开销较低”并不等于“性能一定更好”。最终吞吐仍然受到解码、推理、内存带宽和硬件资源限制。

## 六、真正影响稳定性的几个实现细节

### 1. 心跳必须反映业务进度

一个进程可以正常发送心跳，但它的读帧线程已经卡死。

因此，至少要区分：

| 指标                 | 能说明什么                               |
| -------------------- | ---------------------------------------- |
| 进程心跳             | 管理循环仍在运行                         |
| 最近成功读帧时间     | 采集链路有进展                           |
| 最近完成分析时间     | 分析链路有进展                           |
| 最近成功输出事件时间 | 输出链路有进展，但无事件时不能据此判故障 |

摄像头画面没有变化，不代表没有新帧；没有检测事件，也不代表分析停止。监控应使用处理时间和计数器，而不是业务事件数量代替处理进度。

### 2. 显式预算内部线程

假设每路使用一个模型 Session，每个 Session 又创建多个计算线程，多路运行时就可能产生大量线程争抢。

以 ONNX Runtime 为例，可以显式限制 Session 内的计算线程：

```python
import onnxruntime as ort

options = ort.SessionOptions()
options.intra_op_num_threads = 2

session = ort.InferenceSession(
    "model.onnx",
    sess_options=options,
    providers=["CPUExecutionProvider"],
)
```

这里的 `2` 只是示例参数，应该结合核心数、路数和模型实测调整。官方文档也提供了 Session 线程池及共享线程池的调优说明。[ONNX Runtime 线程调优](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

### 3. 重启顺序要明确

正常停止应先发出退出信号，让采集、分析和输出模块主动释放资源。

超过期限后，再终止进程。强制停止可能导致尚未输出的事件丢失，因此需要可靠交付的事件应配合持久化、重试和幂等设计。

对于分组模式，还需要接受一个事实：重启进程会重置组内所有摄像头的内存状态，包括目标轨迹和业务计时。是否需要恢复这些状态，应由业务要求决定。

### 4. 故障隔离也要考虑摄像头的重要性

负载相近的摄像头，不一定适合分在同一组。

例如，一组设备的网络不稳定，经常触发底层解码异常，就不宜与关键业务摄像头混在同一进程。分组时既要考虑资源均衡，也要考虑故障影响范围。

## 七、如何通过压测决定采用哪种模式？

不要先规定“一个进程最多放几路”，再让业务适应这个数字。

可以在同一台机器、同样的视频输入和模型配置下，对三种模式逐步增加负载，记录：

- 每路实际完成的分析帧率。
- 从应用收到帧到分析完成的 P95、P99 延迟。
- CPU、内存、显存和操作系统线程数。
- 某路断网、读帧阻塞或进程崩溃时，其他路的表现。
- 重启耗时、恢复期间漏处理的数据量。
- 长时间运行后，资源是否持续增长。

测试时还要固定分析帧率目标。一个方案每路分析 2 帧，另一个分析 10 帧，直接比较 CPU 占用没有意义。

如果系统关注摄像头实际拍摄到分析结束的延迟，还需要可靠的源时间戳和时钟同步；应用接收时间只能衡量接收之后的处理耗时。

## 八、选型建议

对于规模较小、希望快速交付的系统，单进程多线程通常是一个清晰的起点。实现重点是采集与分析解耦、限制缓冲，以及监控每路处理进度。

如果单路设备容易出现阻塞或原生库异常，并且业务要求独立恢复，每路一个进程更容易建立清楚的故障边界，但要承担模型和运行时资源重复的成本。

当摄像头数量增加，希望限制故障影响范围，又不希望维护过多独立进程时，可以采用分组多进程。组大小通过压测确定，并结合摄像头负载和业务重要性调整。

这三种模式可以看作对同一个问题的不同回答：**多少路摄像头共享一份进程资源，又允许多少路摄像头一起受到故障影响？**

把这个边界定义清楚，再结合模型实例、线程池和数据流设计，架构选择就有了可验证的依据。
