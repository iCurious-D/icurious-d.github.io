## 为什么需要 LoRA：全参微调的困境

全参数微调（Full Fine-tuning）的问题是：**模型越大越不现实**。

一个 7B 模型全参微调需要 ~112GB 显存（AdamW 优化器状态 + 梯度 + 参数），个人开发者和小团队根本负担不起。更糟的是，每个下游任务都要存一份完整模型，部署成本随任务数量线性增长。

PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）的核心思想：**冻结预训练权重，只训练一小部分新增参数**，让下游任务适配的「增量」最小化。LoRA 是其中应用最广的方法。

## LoRA 的原理：低秩分解

**假设**：模型在下游任务上的参数更新 \\(\Delta W\\) 是「低秩」的——虽然权重矩阵 \\(W\\) 是 \\(d \times d\\) 的大矩阵，但任务适配需要的更新只需要一个低维子空间就能表达。

**做法**：不直接训练 \\(\Delta W\\)，而是训练两个小矩阵的乘积：

\\[ W' = W + \Delta W = W + \frac{\alpha}{r} \cdot BA \\]

其中 \\(B \in \mathbb{R}^{d \times r}\\)、\\(A \in \mathbb{R}^{r \times d}\\)，秩 \\(r\\) 通常取 8~64（远小于 d）。

**参数量对比**：\\(d \times d\\) vs \\(2 \times d \times r\\)。以 4096 维、r=16 为例：1678 万 vs 13 万，**减少 99.2%**。

**几个关键超参**：

| 参数 | 作用 | 常见取值 |
|------|------|----------|
| r（秩） | 可表达更新的维度上限，越大容量越大 | 8 / 16 / 32 / 64 |
| alpha | 缩放系数，实际学习率为 alpha/r | 16 / 32 |
| target_modules | 应用 LoRA 的层 | q_proj, k_proj, v_proj, o_proj（可加 MLP） |
| dropout | LoRA 层的正则化 | 0.05~0.1 |

**为什么 alpha/r？** 让学习率对 r 不敏感：r 增大时自动缩小步长，避免不同 r 配置需要重新调学习率。

## QLoRA：把微调门槛降到单卡

QLoRA 在 LoRA 基础上解决「微调时模型本身也放不下」的问题，三大技术：

1. **4bit NF4 量化**：把预训练权重量化到 4bit 存储，用分位点估计的分块量化（NormalFloat 4），比普通 INT4 更贴合正态分布的权重
2. **双重量化（Double Quantization）**：量化常数本身再量化一次，进一步压缩
3. **Paged Optimizer**：优化器状态溢出到 CPU 内存，用「分页」思想避免显存尖峰

效果：**7B 模型微调从 ~112GB 降到 ~10GB 显存**，单张 3090/4090 就能跑。

## 数据准备：微调成败的一半

### 格式

SFT（指令微调）数据的基本形态：

```json
{
  "instruction": "把下面这句话改写得更正式：",
  "input": "这事儿我得再想想。",
  "output": "此事我需要进一步斟酌。"
}
```

对话模型常用 chat 格式（system/user/assistant 轮次），必须与基座模型的 chat template 对齐。

### 质量原则

- **质量 > 数量**：几百条高质量数据的效果常常优于几万条低质量数据
- **多样性**：覆盖目标场景的表述变体（正式/口语、长短句）
- **分布对齐**：训练数据的风格要与线上真实输入一致，否则微调方向会偏
- **清洗**：去重、去乱码、去「抱歉，作为 AI 助手我不能……」这类模板拒绝语（它会污染模型行为）

## 训练流程

1. **选基座**：优先选与任务语言/领域匹配的开源模型（中文任务选 Qwen 系等），基座能力决定微调上限
2. **格式化数据**：按基座 chat template 组织数据
3. **配置训练**：主流框架是 TRL（SFTTrainer）+ PEFT + bitsandbytes（QLoRA 时）
4. **训练**：1~3 个 epoch，小学习率（1e-4 ~ 2e-4），小 batch + 梯度累积
5. **评测**：保留一份不参与训练的评测集，训练前后对比

```python
# LoRA 配置示例（概念示意）
from peft import LoraConfig

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
```

## 常见踩坑

1. **Loss 不下降**：先查学习率（太大震荡/太小不动）、再查数据格式（chat template 拼错是重灾区）、最后查梯度裁剪
2. **Loss 下降但效果变差**：过拟合（epoch 太多、数据太窄）或评测集与训练集分布不一致。**一定要留独立评测集**
3. **灾难性遗忘**：微调后模型在通用能力上退化。对策：混合少量通用数据、控制 epoch 数、降低学习率
4. **「只会背训练数据」**：数据多样性不足导致模型死记硬背。增加同义改写样本，避免同一 pattern 重复过多
5. **chat template 不一致**：训练用 A 模板、推理用 B 模板，模型输出会明显变差。微调完要保存 template，推理时严格复用
6. **量化 + LoRA 的兼容性**：QLoRA 用 4bit 基座微调，推理时如需合并回 FP16，注意合并精度

## 什么时候微调，什么时候不用

微调不是万能的。决策树：

- **只是要模型遵循特定输出格式** → 先试 Prompt 工程 / 结构化输出
- **需要模型了解私有知识** → RAG 优先（知识更新成本低）
- **需要模型学会新风格/新任务模式**（如特定领域写作、结构化抽取）→ 微调
- **需要大幅改变模型行为或能力边界** → 微调（必要时全参）

**面试常见追问**：「为什么不能只用 RAG 解决？」——RAG 解决「知识从哪来」，微调解决「模型怎么用知识」。知识更新频繁的场景 RAG 更合适；任务模式稳定的场景微调收益更高。两者可以组合：微调让模型更会「用检索结果」，RAG 让知识保持新鲜。

## 小结

- LoRA 的核心是「低秩更新」假设：\\(W' = W + \frac{\alpha}{r}BA\\)，参数量减少 99%+
- QLoRA 用 NF4 量化 + 双重量化 + Paged Optimizer 把 7B 微调降到单卡可跑
- 数据质量决定微调上限，chat template 一致性是隐形杀手
- 微调前先想清楚：Prompt / RAG / 微调，哪个才是真正需要的
