## 为什么 Prompt Engineering 重要

大语言模型的能力上限，往往不是模型本身决定的，而是你给它的指令决定的。同一个模型，给一个好的 Prompt 和一个差的 Prompt，输出质量可能天差地别。

Prompt Engineering 不是什么玄学，本质上就是**用结构化的方式告诉 LLM 你要什么**。本文总结我在实际项目中积累的核心技巧。

## 基础原则：好 Prompt 的四个要素

一个高质量的 Prompt 通常包含四个要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **角色（Role）** | 告诉 LLM 它应该扮演什么角色 | "你是一位资深的 Python 工程师" |
| **任务（Task）** | 明确要做什么 | "请审查以下代码并指出潜在的性能问题" |
| **格式（Format）** | 规定输出的格式 | "以 Markdown 表格形式输出" |
| **约束（Constraint）** | 限定边界条件 | "只关注性能问题，不要修改代码风格" |

```
你是一位资深的 Python 工程师（角色）。
请审查以下代码，指出潜在的性能问题（任务）。
以 Markdown 表格形式输出，包含"代码位置"、"问题描述"、"优化建议"三列（格式）。
只关注性能相关的问题，不要修改代码风格或提出与性能无关的建议（约束）。
```

## Zero-shot 与 Few-shot

### Zero-shot：直接提问

最简单的方式，不给示例，直接让 LLM 回答：

```
将以下文本分类为"正面"、"负面"或"中性"：
"这家餐厅的服务态度非常好，但菜品味道一般。"
```

对于简单任务效果不错，但复杂任务的输出格式和质量可能不稳定。

### Few-shot：给几个示例

在 Prompt 中提供 2-3 个输入-输出示例，让 LLM 理解你期望的模式：

```
将用户反馈分类为情感标签。

示例1：
输入："这个产品太好用了，强烈推荐！"
输出：{"label": "正面", "confidence": 0.95}

示例2：
输入："质量很差，用了一次就坏了。"
输出：{"label": "负面", "confidence": 0.92}

现在请分类：
输入："{user_input}"
输出：
```

Few-shot 的核心价值：
- **规范输出格式**：LLM 会模仿示例的格式，比口头描述格式要求更可靠
- **校准任务理解**：示例比描述更能让 LLM 理解你到底要什么
- **提升一致性**：减少输出的随机性

### 示例怎么选

- **覆盖边界情况**：示例应覆盖不同类型的输入，特别是容易出错的边界情况
- **数量适中**：2-5 个示例通常足够，太多会浪费 token
- **质量优先**：示例的标注质量直接影响 LLM 的输出质量

## Chain-of-Thought（思维链）

让 LLM "想一步说一步"，而不是直接跳到答案。

### 基础 CoT

```
问题：一个班有 30 个学生，其中 60% 是女生。如果 3 个女生转学走了，班上还剩多少个女生？

请一步一步思考。
```

加上"请一步一步思考"这句话，LLM 会展示推理过程，而不是直接给一个可能错误的答案。

### Few-shot CoT

提供带有推理过程的示例：

```
问题：小明有 5 个苹果，给了小红 2 个，又买了 3 个。他现在有几个苹果？
推理过程：
1. 小明初始有 5 个苹果
2. 给了小红 2 个，剩余 5 - 2 = 3 个
3. 又买了 3 个，总共 3 + 3 = 6 个
答案：6

问题：{new_question}
推理过程：
```

### 什么时候用 CoT

| 场景 | 是否适合 CoT |
|------|-------------|
| 数学计算、逻辑推理 | 非常适合 |
| 多步骤分析 | 适合 |
| 简单分类、格式转换 | 不需要，增加延迟 |
| 创意写作 | 不适用 |

## 结构化 Prompt 模板

在实际工程中，我习惯用固定的模板结构组织 Prompt，提高可维护性：

```python
PROMPT_TEMPLATE = """
# 角色
{role}

# 任务
{task}

# 上下文
{context}

# 输出要求
- 格式：{format}
- 语言：中文
- 长度：{length_constraint}

# 示例
{examples}

# 用户输入
{user_input}
"""
```

用 Python 的 f-string 或模板引擎动态填充各字段，便于：
- **版本管理**：Prompt 作为代码的一部分，可以用 Git 追踪变更
- **A/B 测试**：快速切换不同版本的 Prompt 对比效果
- **复用**：相同结构的 Prompt 可以在不同场景中复用

## 常见踩坑与对策

### 坑 1：LLM 不遵守格式要求

**现象**：你要求 JSON 输出，LLM 在 JSON 前后加了一堆解释文字。

**对策**：在 Prompt 末尾加一句"请直接输出 JSON，不要添加任何额外说明"，或使用 `response_format={"type": "json_object"}` 参数（OpenAI API 支持）。

### 坑 2：LLM 编造不存在的信息

**现象**：在 RAG 场景中，LLM 基于检索到的上下文回答时，混入了自己"记忆"中的信息。

**对策**：在 Prompt 中明确约束"仅基于提供的上下文回答，如果上下文中没有相关信息，请回答'资料不足'"。

### 坑 3：Prompt 太长导致效果下降

**现象**：塞了太多上下文和示例，LLM 开始"遗忘"前面的指令。

**对策**：把最重要的指令放在 Prompt 的开头和结尾（LLM 对首尾内容更敏感），中间放上下文信息。控制总长度，精简不必要的示例。

### 坑 4：输出不稳定

**现象**：同样的 Prompt，每次生成的结果不一样。

**对策**：将 `temperature` 设为 0 或接近 0，降低随机性。对于需要确定性的场景（如分类、提取），低 temperature 是必要的。

## 总结

Prompt Engineering 的核心不是背模板，而是理解 LLM 的工作方式——它是一个基于概率的文本生成器，你的 Prompt 就是在调整这个概率分布。好的 Prompt 让 LLM 更容易生成你想要的内容，差的 Prompt 让 LLM 只能猜。

记住三个核心原则：
1. **明确**：说清楚你要什么，不要含蓄
2. **结构化**：用模板组织 Prompt，保持可维护性
3. **迭代**：第一版 Prompt 通常不完美，根据输出反馈持续优化
