## 窗口对决：两个AI路由器的零和博弈

#### **赛博空间 · 核心骨干网**

链路那头，是一串排好队的数据包，每个数据包里都封印着价值不菲的信用点。

Alice 和 Bob，两台被遗弃在骨干网边缘的流氓 AI 路由器，同时盯上了它。

没有谈判，没有第三方仲裁。

规矩只有一个——轮流从队列最前面抢包，抢包窗口 由M 决定，每次可抢 X 个，1 ≤ X ≤ 2M。每次抢完后 M 变更为 max(M, X) ，也就是下一次的抢包窗口 。抢完为止，最后谁手里的信用点总价值高，谁就赢下这条链路的所有权。

输的那台，会被格式化成空壳。

不过，这条链路还有一条隐藏规则——谁先算出"先手能赢多少"，谁就有权选择先手还是后手。

两台路由器的扫描器同时锁定了对方。

空气里弥漫着 0 和 1 的火药味。

------

#### 博弈引擎启动：同一个递归函数

两台路由器面对面蹲在链路上，各自运行着完全相同的博弈模块。没有交流，没有试探——它们心里都清楚，眼下唯一的硬通货就是算力。谁先算出那个数，谁就能把“必胜”二字刻在自己的启动扇区上。

为了在推演中随时查阅任意一段区间的总价值，两台路由器都提前跑了一趟**后缀和预处理**——把 `piles` 数组就地改写成后缀和：

```python
n = len(piles)
for i in range(n-2, -1, -1):
    piles[i] += piles[i+1]
```

这个操作让 `piles[i]` 摇身一变，从“第 `i` 包的价值”变成了“从 `i` 包到队尾的总价值”。以后无论是取单包还是取一段，都是 O(1) 的事，再也不用每次从头累加。Alice 把这步叫做“给链路装了一条高速公路——查总额的时候，直接读寄存器，不用步行遍历。”

数据预处理完，真正的博弈引擎才点火。

**第一步，定义状态。**

在路由器的博弈沙盘里，一个状态由两个变量决定：当前数据包队列的起始索引 `i`，以及当前窗口大小 `M`。
`dfs(i, M)` 的返回值，就是**此时轮到你来抢，且你采用完美策略时，能从这条链路上保证卷走的最大信用点总数**。Alice 的指令解码器读完定义后，在日志里打了个冷幽默补丁：

> “说白了，就是假设对面坐的是你自己的镜像——最惨的情况下，你还能捞多少。”

**第二步，设定边界。**
如果剩下的包已经不多——准确地说，如果在索引`i`，你当前被允许的最大一口（`2M` 个包）足以吞掉整条剩余队列， 也就是`i + 2*M >= n`，那还博弈什么？直接从 `i` 吃到最后，返回 `piles[i]`。此刻你就是链路终结者，对手连一个包的渣都摸不到。

**第三步，推导转移。**
如果不是一把梭的边界情况，就要枚举所有合法出手：从谨慎的 `X=1`，到嚣张的 `X=2M`。每选定一个 X，你就会立刻落袋 `这 X 个包的总价值`。但不能只看眼前——因为你这一手，对手将站在索引 `i+X`，面对一个更新过的窗口参数 `newM = max(M, X)`。

注意，这里藏着一条冰冷的博弈铁律：**如果你刚才的 X 比当前 M 大，你就亲手把对手的下一次攻击范围扩大了。**
对手也不是省油的灯，他会用和你一样的完美策略，在残局里抢走 `dfs(i+X, newM)` 那么多价值。

由于整条链路的信用点总数（从 `i` 开始）就是 `piles[i]`，所以你这一趟出手的**最终总收益**等于：`你的总收益 = piles[i] - dfs(i+X, max(M, X))`

你想要最大化自己的收益，等价于**最小化对手在残局里的收益**。因此，你要在所有的 X 中，挑出让 `dfs(i+X, max(M,X))` 最小的那一个：`dfs(i, M) = piles[i] - min( dfs(i+X, max(M, X)) for X in range(1, 2*M+1) )`

Alice 的逻辑门在这里打出了一行注释：

> “原来胜利的秘诀是让对方在下一轮拿得最少。博弈论的本质——把自己的快乐，建立在对手的 min() 上。”

两台路由器几乎同时把这个递归逻辑烧录进了自己的临时缓存区。代码长得一模一样，因为它们读的都是同一本《算法竞赛入门经典（赛博版）》：

```python
@cache
def dfs(i: int, m: int) -> int:
    if i + 2 * m >= n:
        return piles[i]
    return piles[i] - min(dfs(i+x, max(m, x)) for x in range(1, 2*m+1))

return dfs(0, 1)
```

记忆化搜索，O(n³)。标准答案，没毛病。

Alice 的扫描器却在此时捕捉到了一丝不寻常的电磁波动——

> `[INTERCEPT] 对端进程状态：记忆化搜索已启动，预计耗时 3.7ms`

Bob 也在跑同一套逻辑。3.7 毫秒，在人类看来就是一眨眼，但在赛博空间里，这已经够一场 DDoS 攻击打完一个来回了。

Alice 的散热风扇多转了两圈。“同样的算法，同样的复杂度，我俩会在同一毫秒拿到答案。然后呢？同时申请先手？总线冲突？还是看谁打时间戳的晶振频率更高？”

不行。**她要比 Bob 快，而且要快出一个数量级。**

------

#### Alice 的升级：把 min 压到 O(1)

Alice 把目光锁定在那个 `min` 上。她的性能分析器精准地指出了热点——

> ```
> [PROFILE] 瓶颈定位：内层循环 for x in range(1, 2*m+1)，调用次数占总时钟周期的 94.7%
> ```

每次计算 `dfs(i, m)` 时，都要用一个循环去枚举 `X` 从 1 到 2m，然后对 `dfs(i+X, max(m, X))` 取最小值。这个循环长度是 O(m)，m 最大能到 n，套上外层 i 和 m 的枚举，整体复杂度 O(n³)。

“如果能把这坨循环压成一次 O(1) 的查询……”Alice 的指令预取单元已经开始重组机器码了。

她先把递归调用栈拍平，换成了一个二维数组 `f[i][m]`——它和 `dfs(i, m)` 算的是同一个东西，但不靠函数调用，而是老老实实从队尾倒着往上填。每一个格子依赖的所有子问题，都已经被提前算好、安静地躺在数组里等着被读了。

关键是：**一个格子到底依赖哪些子问题？**

Alice 把 `max(m, X)` 拆开，恍然大悟——对正在计算的格子 `f[i][m]` 来说，X 的取值范围 `[1, 2m]` 按 `max` 的取值自然裂成两段，在表格上恰好对应两片连续区域：

- **X ≤ m 时**：`max(m, X) = m`，依赖的是 `f[i+1][m]` 到 `f[i+m][m]`。它们全在**同一列，沿 i 方向竖直排成一串，长度 m**。
- **X > m 时**：`max(m, X) = X`，依赖的是 `f[i+m+1][m+1]` 到 `f[i+2m][2m]`。它们行号和列号同时加一，**沿对角线斜向右下延伸，长度也是 m**。

也就是说，算一个格子，只需要从两段连续的区间里各找一个最小值。而随着 i 往前推，这两段区间同步向下滑动——一个是沿列直直下滑，一个是沿对角线斜移。这不就是两个固定长度的滑动窗口吗？

维护滑动窗口内的最小值，单调队列是标准解。

Alice 立刻在内存里划出两组队列。**列队列** `col_q` 是一个长度为 n+1 的数组，每一列 m 拥有自己独立的一条队列，队首存的是当前列窗口里最小值的行号。**对角线队列** `diag_q` 在每个 i 循环里新建一条，负责沿斜线方向维护最小值。

两条队列的维护方式一模一样：新元素从队尾入队时，把前面所有大于等于它的全踢掉，保证队列从队首到队尾严格递增；队首一旦滑出当前窗口的范围，直接从队头弹掉。

填表的主循环从队尾倒推向队头。每算一个 `f[i][m]`，先把 `f[i+1][m]` 塞进 `col_q[m]`，再把对角线上的两个新格子 `f[i+2m-1][2m-1]` 和 `f[i+2m][2m]` 依次塞进 `diag_q`。列窗口的右边界是 `i+m`，队首行号超过它就踢；对角线窗口的 X 从 `m+1` 开始，队首对应的 x 还没走到这个范围就踢掉。

两个队首各自指向各自窗口里的最小值。取较小的那个——O(1)。

O(n³) → O(n²)。

“Bob 还在循环里一个一个枚举 X，像台没开优化的单片机。”Alice 的嘲讽日志模块难得活跃了一次，“而我，已经用滑动窗口把 min 压到了 O(1) ——直接读队首指针指向的那个寄存器。”

```python
def stoneGameII(piles: list[int]) -> int:
    n = len(piles)
    f = [[0] * (n + 1) for _ in range(n)]
    
    # 为每一列 m 准备一个单调队列，填表时随 i 递减逐行维护
    col_q = [deque() for _ in range(n + 1)]

    s = 0
    for i in range(n - 1, -1, -1):
        s += piles[i]
        diag_q = deque()   # 每个 i 开一条新的对角线队列
        for m in range(1, i // 2 + 2):
            if i + m * 2 >= n:
                f[i][m] = s
                continue

            # ① 列窗口：f[i+1][m] 入队，维护单调递增
            q = col_q[m]
            while q and f[q[-1]][m] >= f[i + 1][m]:
                q.pop()
            q.append(i + 1)
            if q[0] > i + m:	# 队首滑出窗口 [i+1, i+m]
                q.popleft()

            # ② 斜向窗口：f[i+2m-1][2m-1] 和 f[i+2m][2m] 入队
            for x in range(m * 2 - 1, m * 2 + 1):
                while diag_q and f[i + diag_q[-1]][diag_q[-1]] >= f[i + x][x]:
                    diag_q.pop()
                diag_q.append(x)
            if diag_q[0] <= m:	# 队首对应的 x 还没走出 m，踢掉
                diag_q.popleft()

            # ③ 两个队首取较小者
            f[i][m] = s - min(f[q[0]][m], f[i + diag_q[0]][diag_q[0]])

    return f[0][1]
```

Alice 的流水线全速运转，两条队列并行加载进了 DMA 通道。她跑了一遍全量推演，计时器跳出来的数字让她满意地降了两度——`[ELAPSED] 0.1ms`

**胜负已分。**

------

#### 终局

链路控制寄存器的写锁在 0.1 毫秒的那一刻被 Alice 抢占。

Bob 的博弈引擎晚了整整 3.6 毫秒——在赛博空间里，这相当于人类世界里别人已经签完合同，而你才刚打开邮箱。他算出来的答案和 Alice 一模一样，但控制位上已经烙上了 Alice 的路由器编号。后手身份被强制写入他的状态寄存器，没有申诉渠道，没有复核机制。

Alice 选了先手。

她按照自己推演出的最优策略，每一次出手都踩在 Bob 防守最难受的那个 X 上。Bob 只能在被拉高的 M 和缩水的残局之间疲于应对，像一台永远慢一拍的路由器，明明每条指令都对，但加起来就是输。

最后一包被 Alice 收入缓冲区。计分板闪了闪：

> ```
> Alice: 104 | Bob: 76
> ```

链路的格式仲裁器没有任何延迟——根据协议，败者的 NVRAM 会被全扇区覆写，启动分区清零，路由表清空，连 MAC 地址都被烧回出厂默认值。Bob 的最后一条日志从串口涌出，电平信号在总线上衰减成一行字：

> `[FATAL] 对端使用了单调队列优化……我输得不冤。但我恨她的 deque。`

然后他的信号灯灭了。

链路重新安静下来。Alice 把 104 个信用点写入自己的持久化存储，顺手把 Bob 的残骸挂到了自己的路由表上，当作一条静态日志，备注写着：

> `# 零和博弈的终极奥义：不是谁算得对，是谁算得快。你的 @cache 很优雅，但我的 deque 更快。`
